# Squidify: руководство владельца

Для того, кто отвечает за работу проекта: выкладывает обновления, хранит ключи, помогает пользователям и разбирается, когда что-то сломалось. Здесь нет секретов, только где они лежат и что с ними делать.

## 1. Что где живёт

| Что | Где | Как попасть |
| --- | --- | --- |
| Код | GitHub, репозиторий `BlindSquidHeh/Squidify`, ветка `main` | github.com/BlindSquidHeh/Squidify |
| Сайт | GitHub Pages, собирается автоматически из `main` | https://blindsquidheh.github.io/Squidify/ |
| База, вход, серверные функции | Supabase, проект `olfzaxiokajlhriplooz` | supabase.com/dashboard/project/olfzaxiokajlhriplooz |
| Приложение для Windows | Releases на GitHub | появляется после тега `desktop-v…` |
| Spotify-приложения пользователей | у каждого пользователя своё, в его Spotify for Developers | developer.spotify.com/dashboard |

Ключи и настройки, без которых ничего не работает (значения знаете только вы):

| Имя | Где задано | Для чего |
| --- | --- | --- |
| `SUPABASE_URL`, `SUPABASE_ANON_KEY` | GitHub → Settings → Secrets and variables → Actions → **Variables** | сайт знает, к какому проекту Supabase подключаться. Это публичные значения |
| `SUPABASE_PROJECT_REF` | там же, Variables | `olfzaxiokajlhriplooz`, нужен для деплоя функций |
| `SUPABASE_ACCESS_TOKEN` | там же, **Secrets** | право GitHub Actions выкладывать функции в Supabase |
| `SUPABASE_DB_PASSWORD` | там же, Secrets | пароль базы, нужен только при применении миграций |
| `TOKEN_ENCRYPTION_KEY` | Supabase → Edge Functions → Secrets | ключ, которым шифруются токены Spotify пользователей |
| `ALLOWED_REDIRECT_URIS` | там же | список разрешённых адресов возврата из Spotify: `https://blindsquidheh.github.io/Squidify/callback/spotify/` |

**Что нельзя терять и нельзя показывать никому (в том числе мне в чате):** `TOKEN_ENCRYPTION_KEY`, `SUPABASE_ACCESS_TOKEN`, пароль базы, `service_role` ключ Supabase. Сохраните `TOKEN_ENCRYPTION_KEY` в менеджере паролей. Если ключ потерян или заменён, расшифровать сохранённые токены нельзя: все пользователи просто переподключат Spotify (данные виджетов не пострадают).

## 2. Как выпустить обновление

Любое изменение приходит как pull request. Правило простое: если зелёная галочка CI, можно вливать.

1. **Сайт, редактор, виджет** (папка `web/`): влили PR в `main`, GitHub сам пересобрал сайт. Вкладка Actions → «Deploy site to GitHub Pages» должна стать зелёной (1–2 минуты). Пользователям достаточно обновить страницу (Ctrl+F5). В OBS: правый клик на источнике → «Обновить кэш браузера».
2. **Серверные функции** (папка `supabase/functions/`): после слияния откройте Actions → «Deploy Supabase (migrations + functions)» → Run workflow. Галочку `push_db` **не ставьте**, если не добавляли миграцию.
3. **База данных** (папка `supabase/migrations/`): нужна только когда в PR есть **новый** файл миграции. Тогда запускайте тот же workflow с включённым `push_db`. Старые файлы миграций никогда не редактируются, только добавляются новые.
4. **Приложение для Windows:** в репозитории создайте тег `desktop-v1.0.1` (GitHub → Releases → Draft a new release → новый тег с таким именем). Workflow соберёт установщик и приложит к релизу.

Откат: в PR на GitHub нажмите «Revert» у слитого PR, слейте получившийся новый PR. Для функций после этого снова запустите «Deploy Supabase».

## 3. Первый запуск и проверка, что всё живо

Пройдите сами, как обычный пользователь (лучше в окне инкогнито):

1. Откройте сайт, зарегистрируйтесь, подтвердите email.
2. Создайте приложение Spotify по инструкции на странице «Spotify», подключите.
3. Создайте виджет, вставьте ссылку в OBS или откройте её в браузере: должен показаться текущий трек.
4. Остановите музыку: виджет должен показать сообщение или спрятаться (как выбрано в настройках).

Что проверено в разработке: интерфейс, редактор, база и правила доступа (на настоящей PostgreSQL), серверные функции (типы и проверки), Electron-окно, весь путь «вход → Spotify → редактор → виджет» на подставных данных. **Не проверялась** работа с настоящим Spotify и настоящим Supabase из кода-разработчика (в среде разработки нет ключей), поэтому первый сквозной прогон выше и есть настоящая проверка. Если на каком-то шаге ошибка, сохраните её текст или скриншот.

## 4. Spotify: ограничения, о которых надо помнить

- Приложение в Development Mode: **не больше 5 пользователей**, и у владельца приложения должен быть **Premium**. Поэтому у каждого пользователя свой Client ID, а не один общий.
- «Расширенный доступ» Spotify (без лимита в 5 человек) выдаёт только организациям. Для частного проекта вариант не рассматриваем.
- Общий Client ID технически поддержан (секрет `SPOTIFY_SHARED_CLIENT_ID` в Supabase), но работает только для 5 человек, которых вы вручную добавили в User Management своего приложения.
- Redirect URI должен совпадать с адресом на сайте до символа (с `/` в конце). Если меняете домен или имя репозитория, обновите `ALLOWED_REDIRECT_URIS` в Supabase и Redirect URIs в каждом Spotify-приложении.
- Запрашивается только разрешение `user-read-currently-playing`. Данных о пользователе, плейлистов и истории мы не читаем.
- Правила оформления Spotify обязательны (значок, обложка, ссылки). Они зашиты в редактор, отключить их нельзя. Если когда-нибудь решите брать деньги за проект, правила Spotify меняются, перечитайте их.

Что сказать другу, которого вы зовёте: «Нужен Spotify Premium. Зарегистрируйся на сайте, создай приложение на developer.spotify.com по подсказкам на странице Spotify, вставь Client ID». Ссылка на README вместо длинных объяснений тоже подойдёт.

## 5. Пользователи и лимиты

- Пользователи видны в Supabase → Authentication → Users. Оттуда можно удалить аккаунт или сбросить пароль. Пользователь может удалить себя сам на странице «Аккаунт».
- Письма (регистрация, сброс пароля) идут через встроенную почту Supabase, у неё очень маленький лимит в час. Если людей станет больше нескольких, подключите свою SMTP-службу: Authentication → Emails → SMTP Settings.
- На бесплатном тарифе Supabase: 500 000 вызовов функций в месяц. Один открытый виджет во время музыки делает около 720 вызовов в час, то есть хватает примерно на 690 часов звучания. Если упрётесь, смотрите Supabase → Project Settings → Usage.
- Бесплатный проект Supabase может «засыпать» после недели без обращений. Если сайт перестал работать после долгого простоя, зайдите в панель Supabase и нажмите Restore/Resume.
- Лимиты внутри проекта: 20 виджетов и 50 пресетов на пользователя, конфигурация виджета до 32 КБ.

## 6. Когда что-то сломалось

Начинайте с вопроса, **что именно видит пользователь**: это почти всегда указывает на причину.

| Симптом | Вероятная причина | Что сделать |
| --- | --- | --- |
| Виджет пишет «Неверная ссылка» или «Виджет не найден» | ссылку пересоздали или виджет удалили | дать пользователю новую ссылку из редактора |
| Виджет пишет про ошибку 403 | пользователь не добавлен в User Management своего Spotify-приложения или у владельца нет Premium | объяснить, где добавить аккаунт, проверить Premium |
| «Доступ к Spotify истёк» | пользователь отозвал доступ или удалил приложение | переподключить Spotify на странице «Spotify» |
| Страница Spotify: `INVALID_CLIENT: Invalid redirect URI` | Redirect URI в Spotify не совпадает | скопировать адрес кнопкой с сайта, проверить `/` в конце |
| Сайт: «Этот Redirect URI не разрешён на сервере» | адрес не в `ALLOWED_REDIRECT_URIS` | добавить в секрет Supabase, повторить |
| Пустая страница после выкладки | неверный базовый путь | Actions → смотреть лог сборки сайта, переменная `PAGES_BASE_PATH` или `VITE_BASE_PATH` |
| «Deploy Supabase» красный | неверный токен или проект | прочитать последние строки лога (Actions → красный запуск → «deploy»), чаще всего просрочен `SUPABASE_ACCESS_TOKEN`: создайте новый на supabase.com/dashboard/account/tokens и замените секрет в GitHub |
| Не приходят письма | лимит почты Supabase | SMTP, раздел 5 |
| В OBS старый дизайн | кэш браузерного источника | правый клик → «Обновить кэш браузера» |

Где смотреть логи:

- **Серверные функции:** Supabase → Edge Functions → выбрать функцию (`widget-feed`, `spotify-auth`, `account-delete`) → вкладка Logs. Ошибки там написаны по-русски.
- **Сборка и выкладка сайта:** GitHub → Actions → нужный запуск → нажать на красный шаг.
- **Консоль браузера:** F12 → Console, если ошибка на странице. Скриншот этого окна очень помогает.

Если не получается разобраться: скопируйте текст ошибки (не ключи!) и пришлите в чат проекта.

## 7. Безопасность: что делать, если...

- **Ссылка виджета попала не тому человеку.** Список виджетов → «Новая ссылка». Старая перестанет работать сразу. Доступа к аккаунту Spotify или паролю ссылка не даёт.
- **Утёк `SUPABASE_ACCESS_TOKEN`.** supabase.com/dashboard/account/tokens → удалить токен, создать новый, заменить секрет в GitHub.
- **Утёк `TOKEN_ENCRYPTION_KEY`.** Сгенерируйте новый (в консоли браузера: `btoa(String.fromCharCode(...crypto.getRandomValues(new Uint8Array(32))))`), замените секрет в Supabase и **удалите таблицу токенов** (SQL Editor: `delete from spotify_tokens;`), потому что старые токены зашифрованы старым ключом. Пользователям придётся переподключить Spotify.
- **Утёк `service_role` ключ Supabase.** Project Settings → API → пересоздать ключи, затем перезапустить функции («Deploy Supabase»).
- **Взломан аккаунт GitHub.** Смените пароль, включите двухфакторную защиту, отзовите токены доступа, проверьте Secrets.
- Включите двухфакторную защиту на GitHub, Supabase и Spotify. Это самое полезное, что можно сделать.
- Никогда не добавляйте в репозиторий файлы `.env` и не вставляйте ключи в issues, PR и чат.

Как защищены данные пользователей: токены Spotify зашифрованы (AES-256-GCM) и недоступны из браузера даже самому пользователю; правила доступа к таблицам (RLS) не дают одному пользователю видеть чужое; в ссылке виджета только случайный токен, не связанный с аккаунтом; историю прослушивания сервер не хранит.

## 8. Резервные копии

- Весь код и все миграции лежат в GitHub, схему базы можно создать заново из `supabase/migrations/`.
- Данные пользователей (виджеты, пресеты) на бесплатном тарифе Supabase автоматически не копируются ежедневно. Если они вам важны: Supabase → Database → Backups (на платном тарифе), либо время от времени делайте выгрузку таблиц `widgets` и `widget_presets` (Table Editor → Export to CSV).
- Токены Spotify копировать не нужно: при потере пользователь переподключается за минуту.

## 9. Как вносить изменения в код

Структура:

| Папка | Что там |
| --- | --- |
| `web/src/widget/` | сам виджет: `config.ts` (все настройки и их проверка), `WidgetView.tsx`, `widget.css`, `Visualizer.tsx`, `Marquee.tsx` |
| `web/src/editor/` | редактор: `sections.tsx` (вкладки настроек), `controls.tsx` (ползунки и поля) |
| `web/src/pages/` | страницы сайта |
| `web/src/styles.css` | дизайн сайта (цвета и размеры в переменных в начале файла) |
| `supabase/functions/` | серверные функции |
| `supabase/migrations/` | схема базы |
| `desktop/` | приложение для Windows |

Как добавить новую настройку виджета (например, новый эффект):

1. `web/src/widget/config.ts`: добавить поле в тип `WidgetConfig`, значение по умолчанию в `DEFAULT_CONFIG` и **обязательно** проверку в `normalizeConfig` (любое значение из базы считается недоверенным: цвета, списки и числа проверяются по белым спискам).
2. `WidgetView.tsx` и `widget.css`: применить настройку.
3. `web/src/editor/sections.tsx`: добавить элемент управления на нужную вкладку.
4. Тест в `web/src/widget/config.test.ts`.

Обязательные проверки перед PR (то же запускает CI):

```bash
npm ci
npm run check      # линтер, типы, тесты, сборка
```

Новый пресет: файл `web/src/widget/presets.ts`.

## 10. Чек-лист «я вернулся после перерыва»

1. GitHub → Actions: нет ли красных запусков.
2. Сайт открывается, вход работает.
3. Supabase не «спит» и не упёрся в лимиты (Usage).
4. `SUPABASE_ACCESS_TOKEN` не просрочен (если у токена был срок).
5. Есть ли открытые PR или issues.
